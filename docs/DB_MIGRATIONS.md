# Novala Database Migration Guidelines

**Purpose:** Users must NEVER see database errors during deployments. Every schema change follows these rules.

**Rule of thumb:** If it's not on the SAFE list, it's DANGEROUS. Ask before running.

---

## SAFE Migrations (Users See Nothing)

These can be applied anytime, even while users are on the site:

### 1. Add Nullable Column
```python
op.add_column("employees", sa.Column("nickname", sa.String(50), nullable=True))
```
Why safe: Existing code ignores it. New code opts in.

### 2. Add Column With Server Default
```python
op.add_column("employees", sa.Column("is_active", sa.Boolean(), server_default=sa.text("true"), nullable=False))
```
Why safe: DB fills in default for all existing rows.

### 3. Add Index
```python
op.create_index("ix_employees_email", "employees", ["email"])
```
Why safe: Improves query speed, doesn't change data.

### 4. Add New Table
```python
op.create_table("audit_events", ...)
```
Why safe: Nothing existed before, nothing breaks.

### 5. Add Foreign Key To Nullable Column
```python
op.create_foreign_key(None, "child_table", "parent_table", ["parent_id"], ["id"])
```
Why safe: Existing NULL rows don't get validated.

## DANGEROUS Migrations (Users Can See Errors)

**NEVER do these in a single migration. Use multi-step migration pattern below.**

### ❌ Drop Column
Problem: Any running code that references the column crashes.

### ❌ Rename Column
Problem: SQLAlchemy models must be updated + deployed simultaneously - impossible without downtime.

### ❌ Change Column Type
Problem: Existing data may not fit new type. Running queries crash.

### ❌ Add NOT NULL Column Without Default
Problem: Existing rows have NULL - INSERT statements fail.

### ❌ Drop Table
Problem: Existing queries against table crash. Data lost permanently.

### ❌ Remove Foreign Key Constraint
Problem: Rare but complex - depends on data state.

---

## Multi-Step Migration Pattern (For Dangerous Changes)

### Example: Renaming `employee_name` to `full_name`

**Migration 1 (deploy today):** Add new column
```python
def upgrade():
    op.add_column("employees", sa.Column("full_name", sa.String(255), nullable=True))
```
Deploy. Old code still writes to `employee_name`, new column stays empty.

**Migration 2 (deploy after backfill):** Sync data
```python
def upgrade():
    op.execute("UPDATE employees SET full_name = employee_name WHERE full_name IS NULL")
```
Deploy. Now both columns have same data.

**Migration 3 (deploy code that writes both):** Update application code
- Deploy code that writes to BOTH `employee_name` AND `full_name` in every INSERT/UPDATE
- Reads still use `employee_name`

**Migration 4 (deploy code that reads new):** Switch reads
- Deploy code that reads from `full_name`
- Still writes to both

**Migration 5 (deploy code that only uses new):** Drop old writes
- Deploy code that only uses `full_name`
- Old column still exists but is unused

**Migration 6 (weeks later, after monitoring confirms no code uses old):** Drop old column
```python
def upgrade():
    op.drop_column("employees", "employee_name")
```

**This process takes 2-4 weeks minimum.** That is the price of zero downtime.

## The Alembic Autogenerate Problem

`alembic revision --autogenerate` compares SQLAlchemy models to DB schema.

**PROBLEM:** If your models don't reflect the ACTUAL production DB state, autogenerate will suggest:
- Dropping tables you forgot to add to models
- Deleting indexes that exist but aren't in models
- Removing columns that were added by other developers

**RULE:** NEVER trust autogenerate. ALWAYS write migrations manually.

### Safe Alembic Workflow

```bash
# 1. Create empty migration
./venv/bin/alembic revision -m "add feature_flags table"

# 2. Manually write ONLY the changes you want in the upgrade() and downgrade() functions

# 3. Test locally first
./venv/bin/alembic upgrade head

# 4. Test rollback
./venv/bin/alembic downgrade -1

# 5. If both work, apply to staging, then production
```

## Rollback Requirements

**Every migration MUST have a working `downgrade()` function.**

If the migration adds a table:
```python
def upgrade():
    op.create_table("foo", ...)

def downgrade():
    op.drop_table("foo")
```

If the migration adds data via SQL:
```python
def upgrade():
    op.execute("INSERT INTO ...")

def downgrade():
    op.execute("DELETE FROM ... WHERE ...")
```

**If you can't write a downgrade, don't run the migration.**

## Pre-Deployment Checklist

Before applying any migration to production:

- [ ] Migration written manually (not autogenerated)
- [ ] Only contains changes for THIS feature
- [ ] `upgrade()` and `downgrade()` both work locally
- [ ] `alembic downgrade -1` successfully reverts
- [ ] Tests pass with migration applied
- [ ] Tests pass with migration reverted
- [ ] Reviewed by second person (or Claude)
- [ ] Backup of production DB taken
- [ ] Deployment window scheduled if change is DANGEROUS

---

## Emergency Rollback

If a migration causes production issues:

```bash
# On the server
cd ~/novala/backend
./venv/bin/alembic downgrade -1
sudo systemctl restart novala-backend  # or however you restart
```

Time from problem detected to rollback complete: **should be under 5 minutes**.

---

## Common Mistakes To Avoid

1. **Trusting autogenerate** → always write manually
2. **Dropping columns immediately** → use multi-step pattern
3. **Renaming columns** → use multi-step pattern
4. **Adding NOT NULL without default** → make nullable first, backfill, then NOT NULL
5. **No downgrade function** → won't be able to rollback
6. **Big-bang migrations** → break into small independent steps
7. **Skipping local testing** → always test upgrade AND downgrade locally first
